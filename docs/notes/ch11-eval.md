## 觀察

1. **Hybrid 解決了精確字串**：questions.jsonl 的精確編號題（HR-2026、ABC-123、第7條之1、第三條之一）從 dense 的 0% 進入 Context，到 hybrid 的 4/5；新增的編號題 6/6、條號題 6/6 都在前 3 名。剩下的 q24「115 年 3 月 18 日」是日期，不在精確詞的規則內（英數編號、條號、引號字串），維持被擋下。
2. **語意改寫題 Recall@5 不變，但 Recall@1 下降**（92% → 75%）：q09「特休沒休完可以延到明年嗎？」、q10「剛進公司半年有幾天特休？」的第 1 名從管理辦法第十二條變成新進員工指南的 FAQ（內文有「特休」與「第十二條」，在關鍵字清單排得前面，RRF 加分後超過）。正確條文仍在前 5 名、會送進 Context，但排序變差；這正是下一章 Reranker 要處理的。
3. **兩種 keyword_only_policy 的結果完全相同**：
   - 專有名詞題（p01～p04）在所有模式都是「無候選」：人名抽不出精確詞，Dense 分數也沒過門檻，而**資料不足的判斷不看一般關鍵字**，所以 allow 也救不回來。這是設計上的取捨：不讓「人資部門」這類常見詞把無答案題帶進 LLM。
   - 通過判斷的題目，僅被一般關鍵字找到的段落在 RRF 中排在後面，沒有改變預期段落的名次。
   - 想讓 allow 有作用，需要讓一般關鍵字也能通過判斷（例如 FULLTEXT 分數門檻），但分數尺度隨查詢變動，本章不做。
4. **新的無答案題暴露的是 Dense 門檻的問題**：n01「員工旅遊的規定是什麼？」Dense 0.6357、n04「人資部門在公司的幾樓？」0.6056，都超過 0.59，dense 模式也一樣放行。只有 keyword 模式 6/6（因為只有精確命中才算），代價是語意題全部找不到。門檻 0.59 是暫定值（backlog #8），新的題型讓它的限制更明顯。
5. **keyword 單獨使用不可行**：用詞相同、換句話說題 Recall 都是 0%（問題整句做 NATURAL LANGUAGE 查詢，加上只有精確命中才算候選）。
6. **實作中發現的陷阱：1 字的編號片段**。`ngram_token_size = 2` 時，「HRIS-3」被連字號切成「hris」與「3」，「3」不進索引，片語查詢整個查不到（第一次評估 c06 未命中）。`SearchTextNormalizer` 改為移除英數字之間的連字號（「hris-3」→「hris3」），建立索引與查詢一致，回填後 c06 排第 1。`fulltext` 群組新增 `test_code_with_single_character_segment_is_found`（紅綠驗證）。
